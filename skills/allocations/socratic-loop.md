# Socratic loop — canonical batch validation + 4-state machine + edits-log

> **Reference-only.** This file is not a skill — it has no `SKILL.md` and never triggers.
> Skills that run a Socratic validation pass (`specify`, `design`) read this file for the
> canonical machine and keep only a short **delta** of their own decision-types and section list.

## Contract — batch-per-section, not per-decision-across-sections

For each section/group in order, the skill:

1. **Render the full proposed section** in one message — body text + a numbered list of the decisions it contains. The user sees the whole shape before any per-decision commitment (they catch duplicates / gaps / drop-the-whole-section problems early). Then offer the **section fast path** (below) when the section qualifies.
2. **Walk per-decision resolutions** — using the 4-state machine below, **batched** up to 4 decisions per `AskUserQuestion` call (see *Batching*).
3. **Apply transitions** to the section as each resolution arrives (for a batch: in decision order, after the whole batch returns).
4. **Run any per-skill gate** on Approved decisions (e.g. `design`'s blast-radius gate → ADR). Edit/Drop/Save-as-OQ do not trigger gates.
5. **Write the resolved section to disk** + any files the gate spawned — immediately, **no commit**. Commits happen once at the end of the step, one per document, after the structural self-check ([write-and-commit.md](./write-and-commit.md)).
6. **Move to the next section.** The skill **never returns** to a written section — cross-section drift is the critic's job, not a re-walk.

The artifact file was bootstrapped from its template at the first write point; each section lands in it at step 5, so an interrupted session keeps every section already resolved.

### Section fast path — «Approve whole section»

After the render in step 1, ask **one** `AskUserQuestion` before the per-decision walk:

- `Approve whole section` — every decision in the section is resolved as `Approve` in one go: the per-skill gate runs on each one (in order), then step 5 writes the section. No edits-log entries (Approve is the baseline).
- `Walk each decision` — the normal batched walk (step 2).

Offer the fast path **only** when the section has ≥2 decisions **and** none of them is high-stakes — i.e. none would fire the per-skill gate on its own (e.g. `design`'s blast-radius → ADR, or a «Lock as ADR or inline?» borderline), and none touches a coverage floor the user hasn't seen resolved yet. A section with even one such decision goes straight to the walk; say why in one line («§4 contains a strategic decision that spawns an ADR, so I'll walk it»). At `easy` depth the assumptions ledger already covers reversible calls, so the fast path applies to whatever is left to walk. If the user picks «Other» and names specific decisions («approve all but #3»), approve the rest and walk only the named ones.

### Batching — up to 4 decisions per call

`AskUserQuestion` takes up to 4 questions per call. Group decisions of the **same section**, in order, into calls of ≤4, so the user resolves a group per round-trip instead of one decision at a time. Each question in a batch still follows [style.md](./style.md) in full (context, why it matters, glossed options) — batching reduces round-trips, never explanation.

Ask a decision **alone** (a batch of one) when:

- it **depends on** another decision in the same section (its options change depending on that answer — e.g. `design`'s UI-architecture follows the Surface pick); ask the upstream one first;
- it is **high-stakes** — it would fire the per-skill gate (ADR spawn) or it is a mandatory decision whose Drop triggers a re-ask; the user should weigh it without other questions competing for attention;
- it is a **follow-up** generated by a resolution (Edit round 2, the Save-as-OQ owner+due capture, a mandatory-Drop re-ask, a coverage-floor mini-batch) — follow-ups run right after the batch that produced them, before the next batch.

Follow-ups from different decisions in the same batch may themselves be batched together (≤4), as long as none of them is high-stakes.

## The 4-state machine (uniform across every decision-type)

- **`Approve`** → keep the decision verbatim. No edits-log entry (Approved is the baseline). Run the per-skill gate if any. Move on.
- **`Edit`** → user supplies new wording / option / value in one go; skill regenerates the decision under the new constraint and asks **once more** (single-iteration cap — the second answer is final). Log entry `action: "edit"`.
- **`Save as Open Question`** → decision leaves its native section and a row is appended to the artifact's Open-Questions / Risks table:

  ```
  | Open decision: <headline> | Open question | Resolve before <stage trigger or YYYY-MM-DD>; <inline rationale> | <owner> |
  ```

  Owner + due (a date OR a stage trigger like «before `foresdd:tasks`») are **mandatory** — issue a follow-up `AskUserQuestion` to capture both. If either is left blank, **downgrade to `Drop`** with an explicit warning. Log entry `action: "save_as_oq"`. **No gate** — a defer is not an accepted decision.
- **`Drop`** → decision is removed. Two sub-paths:
  - **Mandatory decision** (e.g. a module boundary that every feature must have) → re-ask **once** with a reframed option set. Second drop → escalate to `Save as Open Question` with a skill-suggested owner + due and a warning.
  - **Optional decision** → leave it out, no replacement.
  - Log entry `action: "drop"` (`after: null`).

Each option `label` is the **next mechanical step**; each `description` explains what the skill will do — see [style.md](./style.md).

## Edits-log (mandatory)

After each `Edit` / `Drop` / `Save as Open Question` (NOT `Approve`), append one entry:

```
{decision_id: "DEC-<section>-<short-id>",
 action:      "edit" | "drop" | "save_as_oq",
 before:      "<verbatim wording/option/value before the action>",
 after:       "<verbatim wording after — for save_as_oq this is the OQ-row text incl. owner+due; for drop, null>",
 user_reason: "<the rationale the user gave, verbatim>"}
```

`Approve` decisions stay out of the log — they are the baseline. The log is the **sole** signal the clean-context critic uses to detect upstream-coherence drift caused by user edits. Without it the critic has no input for its F-classes. If the user gives no reason on `Drop` / `Save as OQ`, re-prompt once — verbatim wording matters to the critic.

## Cadence

- **Progress marker on every question.** Each question shows where the user is, as the first line of the question text: `§<n> <section name> · decision <k>/<total in section> · section <i> of <N>` (e.g. `§5 Building blocks · decision 3/7 · section 5 of 12`). The `header` chip carries the short form (`§5 · 3/7`). Follow-ups keep the parent decision's marker with a suffix (`§5 · 3/7 · follow-up`). The user always knows how much is left.
- A 1-line mini-recap of decisions so far every ~5 questions (count individual decisions, not calls), so the user sees the dependency chain without scrolling.
- **Pass summary before the critic.** When the last section is written and before the critic is dispatched, print one summary message: per section, the counts `approved · edited · deferred (OQ) · dropped`, then totals, then every Open-Questions row added this pass (headline + owner + due), and for skills with a gate the spawned files (e.g. ADR ids + titles). This is a recap, not a question — no re-walk; the user can react in free text, and any change they ask for goes through the critic phase.
- Keep a soft question budget per section sized to the feature class (see [tshirt-sizing.md](./tshirt-sizing.md)): XS/S lean on `<!-- N/A -->`, M+ walk every decision.
- **Question volume also scales with the interview-depth dial** ([interview-depth.md](./interview-depth.md)): `easy` decides the reversible calls itself and walks only the irreversible/high-stakes ones (stating its assumptions in a ledger), `medium` walks every real decision, `hard` walks every decision and foregrounds each trade-off. Depth and size compound — an XS feature at `easy` asks the least; an L feature at `hard` asks the most. Volume only: the disk-write discipline, the edits-log, and any coverage floor are unaffected by depth.

## Exit condition

A section is done when every decision in it has exactly one resolution applied, the resolved content + any gate-spawned files are on disk, and the edits-log has no pending entries. The whole pass is done when all sections are written, the pass summary has been shown, and (for skills that run one) the critic phase has been dispatched — see [critic.md](./critic.md).

## Per-skill delta (what each consuming skill defines locally)

A consuming skill's `references/socratic.md` (or an inline ≤5-line block in `SKILL.md`) supplies only:

- **Section/group list** walked in order (e.g. `specify`: the 5 AC coverage types; `design`: Arc42 §1–§12).
- **Decision-types catalog** for this artifact (e.g. `design`: Strategic / Building-block / Crosscutting / Quality-scenario / Risk).
- **Per-skill gate** run on Approved decisions, if any (e.g. `design`: blast-radius → ADR).
- **Open-Questions table location** (which section absorbs `save_as_oq` rows).

A per-skill decision-type may add an extra action, but the total option count must stay **≤4** (the `AskUserQuestion` limit). The built-in free-text «Other» answer is the place for a 5th action (e.g. `specify`'s «add another AC»).

Everything else — the 4-state machine, the edits-log schema, the cadence, batching, the section fast path, the progress marker and pass summary — comes from this file; the disk-write + commit discipline comes from [write-and-commit.md](./write-and-commit.md).
